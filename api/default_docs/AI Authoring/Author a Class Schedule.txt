CLASS SCHEDULE & CALENDAR AUTHORING
Version 2.0

Use this guide when helping a teacher finish Calendar schedule setup. There
are three parts, all stored in the teacher's local workspace:

1. Teacher Schedule.json maps unique stable block names to the bell periods for each class.
2. Bell Schedule CSV files define the ordered meetings and their actual start and end time. These
   are teacher-owned files in the Calendars folder.
3. School Calendar.json is the one canonical date authority: for every date in its coverage, it
   names the day's kind (instructional / no_regular_classes / no_school) and, for instructional
   days, which Bell Schedule applies.

TEACHER SCHEDULE AND BELL SCHEDULES

Use get_teacher_schedule to read the existing blocks before changing them. A block's name is the
 binding key that a classroom display points to. Keep it steady once displays use it. The block label
is display text only and may repeat. Do not derive a name from a course title or from the label.

raw_periods names the bell meeting IDs claimed by a block. The School Calendar chooses the bell
schedule for each date, so the same Teacher Schedule works for an exam day, an early-release day,
or a schedule that runs on an unusual weekday. Do not add a weekdays field. Block names and
period IDs must be unique across the saved schedule. A block absent from a day's bell schedule
is silently absent that day; save_teacher_schedule catches a period ID that exists in no Bell
Schedule CSV.

Bell Schedule CSVs require period_id,start,end and may include label. start and end use the
teacher-facing local clock format h:mm AM/PM (for example, 8:35 AM or 3:55 PM), never 24-hour
military time. They are ordered by start time when read. Duplicate period_id values are legal:
a review meeting and a later exam can both use period 6. A block spanning consecutive claimed
meetings resolves to one window. If another meeting interrupts it, it resolves to separate
windows; a slide bound to that block uses the first window. Call get_bell_schedule to read
available schedule_ids; never invent one.

THE SCHOOL CALENDAR

Call get_school_calendar first: with no arguments it returns readiness only (whether a calendar
exists, today's resolved state, and any low-coverage warning); with date_from and date_to it also
returns the day/grading-period/event rows in that range.

To build a complete year from scratch (or replace one entirely), use
preview_school_calendar_replacement then apply_school_calendar_replacement:

1. Call preview with school_year, coverage_start, coverage_end, and default_schedule_id. Every
   date in the requested coverage becomes instructional (on the default schedule, or a
   weekday_schedules override), a generated weekend, or an explicit no_school_dates/
   no_regular_classes_dates entry you pass in. There is no partial creation — a full year is
   validated as one unit.
2. The preview returns operation ("create" when no calendar exists yet, else "replace"),
   base_revision (0 for a first-ever calendar), the current and proposed school year/coverage,
   and material change counts. Summarize this to the teacher in plain language — a replacement
   overwrites every date in the new coverage — and get their confirmation before applying.
3. Call apply with that same preview object and expected_revision set to its base_revision. A
   stale revision (the calendar changed since your preview) is refused rather than silently
   reapplied — preview again if that happens.

For a one-off or short-range correction to an existing calendar (a snow day, a pep-rally
schedule for one date, "use Friday Schedule Monday through Friday for the next two weeks"),
use preview_school_calendar_change then apply_school_calendar_change:

1. Call preview with either an explicit dates list or a date_from/date_to range (optionally
   narrowed with a weekdays subset), plus the target kind (instructional / no_regular_classes /
   no_school), a schedule_id (instructional only), and a label (required for the other two
   kinds).
2. The preview returns base_revision and the affected dates' before/after values. Summarize
   this to the teacher in plain language and get their confirmation before applying.
3. Call apply with that same preview object and expected_revision set to its base_revision. A
   stale revision (the calendar changed since your preview) is refused rather than silently
   reapplied — preview again if that happens.

Do not invent a day kind, guess a schedule_id, or skip the preview step. Weekends and holidays
are never implied — every date in coverage is an explicit row, so a corrected date is exactly as
authoritative as any other.

When the teacher is ready, call save_teacher_schedule with the complete blocks list. These tools
write the local files directly, with no staging queue. They return counts, revisions, and paths
rather than every generated row.
