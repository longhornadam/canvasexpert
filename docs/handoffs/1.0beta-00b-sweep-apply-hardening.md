# 1.0beta slice 00b — sweep apply hardening

Status: **QUEUED** (run after 00a is accepted)

Risk: **high** — grade-adjacent write boundary (`seconds_late_override` mutations).

Depends on: 1.0beta-00a accepted (no code dependency; sequencing only).

## Teacher-visible result

Applying a late-work sweep can no longer write whatever the browser submitted. The apply
step recomputes the sweep from authoritative Canvas state (or executes through the
operation-ledger sweep adapter) at apply time, so a stale preview tab, a modified request,
or drifted Canvas state cannot push wrong `seconds_late_override` values. Preview remains
fast and unchanged in appearance.

## Background (established truth)

`/api/sweep/apply` (`api/webui/routes/gradebook_sweep.py:29-53`) JSON-decodes the
browser-submitted `entries` form field and PUTs each row's `seconds_override` to Canvas
using client-supplied `assignment_id`/`user_id`, with no recompute and no drift check.
Meanwhile a complete `SweepAdapter` already exists at
`api/operation_ledger/adapters/sweep.py` with `build_payload`, `capture_baseline`,
`check_drift`, `freeze_review`, idempotency keys, `execute` (writes
`seconds_late_override`), `reconcile`, and receipts. The vision doc (§11.5, §13.4, §21
item 9) marks this a release blocker; the locked decision is to reuse the adapter, not
build a second recompute path.

## Locked design for this slice

Route sweep apply through the operation-ledger `SweepAdapter`.

1. The apply route stops trusting `entries`. It accepts the sweep **settings** (the same
   input `sweep_preview` takes) plus whatever review/confirmation token the ledger
   pattern requires, and drives the ledger sequence: build payload → capture baseline →
   drift check → freeze → execute → reconcile → receipt.
2. Browser-submitted entries may still be sent for **display-diff purposes only** (e.g.,
   to warn "Canvas changed since your preview"), never as the write set. If diffing is
   more than trivial, drop it and rely on the adapter's own drift check.
3. Preview (`/api/sweep/preview`) is unchanged.
4. Response shape to the frontend may change minimally; update the calling JS in the same
   slice so the sweep UI still completes end-to-end.
5. No new persistence, no schema changes, no mirror involvement — this is a live write
   boundary per design law 5.7.

Forbidden: keeping the direct-PUT path alive "for compatibility"; adding a second
recompute implementation beside the adapter's `_compute_sweep`.

## Execution result

**Traffic light:** RED — stopped at preflight, no implementation changes made.

**Evidence:**

Preflight facts 1 and 3 hold:
- `sweep_apply` (`api/webui/routes/gradebook_sweep.py:29-53`) decodes `entries` from the
  form and PUTs `seconds_late_override` directly; no `_sweep_compute` call.
- `sweep.js` (`api/webui/static/gradebook/sweep.js:134`) posts preview `rows` straight to
  `/api/sweep/apply`.

Preflight fact 2 (the stop-if-false condition) is **false**:
`SweepAdapter` is registered in `api/operation_ledger/adapters/__init__.py` /
`registry.register(SweepAdapter())`, and `api/operation_ledger/adapters/sweep.py` fully
implements `build_payload`/`capture_baseline`/`check_drift`/`freeze_review`/`execute`/
`reconcile`/`idempotency_key` — but it is not reachable through any HTTP route today, and
no other gradebook operation reaches the ledger either:

- `CurveAdapter` (`gradebook.curve`) and `LatePolicyAdapter` (`gradebook.late_policy`) are
  registered the same way, but the live routes that actually run curve/late-policy
  (`api/webui/routes/gradebook_curves.py:102-160` `curve_apply`, and
  `api/webui/routes/gradebook_policy.py:22-46` `apply_late_policy`) contain **their own
  direct `_canvas_send` PUT/PATCH logic** and never call `registry.get_adapter(...)`,
  `executor.apply_operation`, or any ledger primitive. `ExtensionAdapter`
  (`gradebook.extension`) likewise has no calling route at all — `extend_due` in
  `api/webui/routes/gradebook_extensions.py` also bypasses the ledger with a direct
  Canvas override POST.
- `rg -n "registry\.get_adapter|executor\." api/webui/routes/*.py` (all route files)
  matches only `api/webui/routes/operations.py`, which exposes the **generic**
  `/api/operations/{kind}/prepare` -> `/api/operation-batches/review` ->
  `/api/operation-batches/{batch_id}/apply` three-step flow. Its only caller is
  `api/webui/static/push/core.js`, which drives it exclusively for **content** kinds
  (`content.page`, `content.quiz`, etc., via `pushContent`/`operationKinds`) — never for
  any `gradebook.*` kind.
- `test_curve_operation.py`, `test_late_policy_operation.py`, `test_extension_operation.py`,
  and `test_sweep_operation.py` all import the adapter classes directly and call
  `registry.get_adapter("gradebook.…")` at the unit level; none use `TestClient` or go
  through an HTTP route. The one hit for `"gradebook.sweep"` in `test_desk_routes.py`
  is a synthetic Home-receipt fixture string, not a dispatch path.

Conclusion: the four gradebook operation-ledger adapters (sweep, curve, late_policy,
extension) are fully built and unit-tested, but **none of them are wired to any HTTP
route** — every gradebook write route today (including today's broken sweep apply)
bypasses the ledger with hand-rolled Canvas calls. The only working "HTTP route ->
ledger adapter execution" path in the repo serves content-push operations, in a
three-step prepare/review/apply UX that has never been used for a gradebook operation.
Routing `/api/sweep/apply` through that generic mechanism would mean building the
gradebook domain's first-ever integration with it (new frontend flow, new response
shape, first real-world exercise of `SweepAdapter.execute`/`reconcile` outside unit
tests) — that is exactly the "wiring new dispatch infrastructure" the brief marks as
senior scope, not a mirror of an established gradebook pattern.
