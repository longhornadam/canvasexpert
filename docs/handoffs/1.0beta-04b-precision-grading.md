## Senior decisions that shaped the build (with rationale)

1. **Convergence model = write-through refresh, NOT invalidate** (for ordinary
   submissions). Submissions freshness is *sync-watermark-driven*:
   `read_service.private_submissions` derives course-level `current`/age from the
   `read_sync` full/delta pass stamps, **not** from any per-assignment file
   `state`. So a groups-style per-assignment `invalidate_submissions` (analogous
   to `store.invalidate_groups`) would **not propagate** to what
   `mirror_reads.submissions_or_live` serves. The codebase already ships the
   right primitive: `mirror_service.notify_course_changed` →
   `sync.refresh_submissions_course_delta` (`api/mirror/sync.py:142`), a
   *"write-through refresh [that] converges private submission facts promptly"*
   by re-reading the reused submitted/graded-since window **without advancing the
   watermark**. Batch B wires this once per verified write-batch.
2. **Lift the `cached_due_date`/`seconds_late` deferral now** (A). 04a had
   explicitly deferred these; Batch 4 is their consumer batch. The submissions
   validator does not exact-key the inner `current` dict
   (`store.validate_submissions`, `api/mirror/store.py:308`), so adding fields is
   **not** a schema bump.
3. **New Quiz freshness = two independent surfaces** (D): the gradebook
   submission score (converge via the same write-through refresh) AND the
   *separate* per-student New-Quiz response cache (stale-invalidate only). An
   eager response re-read would drive the native/report chain as a
   freshness-triggered write path → **crosses the transport boundary, not done**.

### D — New Quiz freshness after finalize (`5f3b66a`)
- `api/mirror/new_quizzes.py`: new `invalidate_responses(course_id,
  assignment_id, *, root, attempted_at)` — flips the per-assignment responses
  envelope to `stale` via `_record_sync(kind="responses", state="stale")`.
  Mirrors `store.invalidate_groups`: missing/never-fetched snapshot is a no-op,
  never writes `current`. Next `read_fresh_snapshot` returns `(None, "stale")`,
  so `assignment_refresh` falls back through the **existing** live native chain.
- `api/webui/routes/powergrader.py`: `_converge_new_quiz_after_finalize(session,
  user_id)` calls `_notify_write_through` + `invalidate_responses`; wired into
  `pg_new_quiz_finalize` only when `payload["status"] == "finalized"` (not
  `already_applied`).
- `new_quiz_grader._verify_applied` (`api/powergrader/new_quiz_grader.py:235`)
  verifies the write live/in-memory but touches **no** mirror — convergence is
  entirely the finalize-route wiring above.

## Known caveats / limitations
- **New Quiz gradebook convergence is eventual, not deterministic.** The native
  results POST hits the LTI quiz host; Canvas syncs the score to the gradebook
  asynchronously, so `graded_at` may not be bumped when the 15s-delayed delta
  fires — it converges on that-or-a-later tick. `notify_course_changed`'s
  docstring even disclaims New-Quiz freshness. If deterministic convergence is
  later required, that needs a targeted post-sync verify (design it to stay
  inside the transport boundary — no persisted signed URLs/tokens/host).
- Convergence for the **late-sweep** override is best-effort: a
  `seconds_late_override` change may not land in the `graded_since`/
  `submitted_since` delta window; the sweep adapter's own `reconcile` (sample
  verify) is the stronger check there.
