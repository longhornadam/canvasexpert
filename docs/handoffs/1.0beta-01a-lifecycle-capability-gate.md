known-forbidden New Quiz calls. Concluded/retired courses show their New Quiz scope as

## Background (established truth)

New Quiz endpoints are gated on **active enrollment** (`api/README.md` ~205-213): the same
token returns 200 in an actively-enrolled course and 403 in a concluded/past-enrollment
course. This is confirmed in production use. Today `sync_metadata`
(`api/mirror/new_quizzes.py:674-728`) fans out one GET per New Quiz per pass
(`/api/quiz/v1/courses/{c}/quizzes/{a}`, line 696); `_metadata_is_current` (line 660)
skips only previously-successful quizzes, so a 403-ing quiz retries every heartbeat
(`api/webui/mirror_service.py`, `TICK_SECONDS = 900`). No lifecycle or capability signal
is stored anywhere; `run_heartbeat_pass` iterates `config.active_courses()` — a pure
config-membership list. Design: **lifecycle predicts, probe confirms, circuit backstops**
(vision doc §9.4).

## Locked design for this slice

### 1. Per-course New Quiz capability record (student-free)

Persist a small capability envelope for the New Quiz metadata scope per course, stored
with the existing course sync-envelope machinery in `api/mirror/store.py` (same atomic
write and last-good rules). Allowed fields only:

- `capability`: `"supported" | "restricted" | "unknown"` (`"unsupported"` reserved, unused
  for now);
- `last_probe_at`, `retry_after`: ISO-8601;
- `evidence`: stable sanitized category (`"forbidden"`, `"unauthorized"`) plus consecutive
  failure count.

Forbidden at rest: status text, response bodies, URLs, quiz titles, any student data.

### 2. Classification rule (locked — do not re-derive)

The enrollment gate makes New Quiz 403s course-level. Rule: **3 consecutive distinct-quiz
`HTTP 403`/`HTTP 401` failures with zero successes in the same `sync_metadata` run →
`capability = "restricted"`, `retry_after = now + 24h`.** Any single success in a run
resets the scope to `supported` and clears the cooldown. Mixed runs (some 200, some 403)
remain `supported` — those failures are item-level noise and keep today's behavior.
Classify by parsing the `HTTP 403`/`HTTP 401` prefix of the existing error string; do not
rewrite `canvas_client` error handling in this slice.

### 3. Gate in `sync_metadata`

At entry: if the stored capability is `restricted` and `now < retry_after`, skip the
entire fan-out and record the scope as skipped-restricted. When `retry_after` passes, the
next run performs **one bounded probe** (the first quiz in the list); a 403/401 renews the
cooldown without touching the remaining quizzes; a success clears it and proceeds
normally.

### 4. Manual override

`sync_now(course_id)` (explicit manual sync) ignores the cooldown and performs a full
probe — the manual-diagnostic override from vision §9.3. The 15-minute heartbeat never
ignores it.

### 5. Sanitized visibility

Count skipped-restricted runs and circuit opens/clears in whatever sanitized sync summary
`_record_sync`/heartbeat already produce, so 01a's effect is observable. Course alias or
synthetic ID only; no course names.

Out of locked scope but explicitly noted for the senior: probing
`GET /api/quiz/v1/courses/:id/quizzes` (collection) as a one-call probe/bulk source is a
Program 0 investigation; this slice keeps the per-quiz endpoint.
