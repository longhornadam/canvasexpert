# Give Roster a private, invalidated group-context snapshot

Status: **GREEN; completed**

Risk: **high** - group membership and stable student IDs are FERPA-protected; stale local membership must never drive a Canvas mutation.

Depends on: current `dev` after `a89f02d`

## Teacher-visible result

Reopening Roster can reuse a fresh private group-context snapshot rather than repeating the
live category/group/membership fan-out. A missing, corrupt, stale, or post-mutation snapshot
uses the existing live group loader. Every group membership/category/group write still
validates and executes against live Canvas state.

## Acceptance criteria

- [ ] Add a strict private `groups.v1.json` mirror document containing only course ID,
  sanitized envelope metadata, category IDs/names, group IDs/names, and membership
  `{id,user_id}` pairs. It stores no student names, email, arbitrary Canvas fields, raw
  errors, credentials, URLs, or filesystem paths.
- [ ] `GET /api/roster` uses this snapshot only while it is exactly `current` and less than
  24 hours old, converting it to the existing category/group shape used by Roster helpers.
  That path makes no `load_group_categories` call and preserves the current JSON response,
  warnings, group labels, and selection behavior.
- [ ] On missing/corrupt/stale/unavailable snapshot, Roster invokes the existing live
  `load_group_categories` behavior unchanged. A successful, error-free normalized live
  result replaces the snapshot; a live failure never overwrites last-good private groups.
- [ ] Every successful Roster group membership change and group/group-set creation invalidates
  the snapshot after the existing live write succeeds. Failed writes leave local group state
  untouched. The next Roster read therefore uses the existing live loader.
- [ ] No Roster write validates against cached groups; no direct-transport ownership,
  scheduler/heartbeat, Course Info, Create, browser asset/template, or workspace schema
  other than this dedicated private snapshot changes.
- [ ] The named acceptance gate below passes.

## Explicit non-goals

- No group background pass, generic coordinator, Course Info migration, Home warning
  migration, group projection consumer outside Roster, or change to the existing Canvas
  group transport/fallback policy.
- No cached group state for operation-ledger preflight, membership write verification, or
  group creation validation.
- No persistence of group member names, user profiles, section membership, Canvas URLs,
  or raw membership response fields.

## Locked decisions

- Keep `groups.v1.json` beside other private mirror files, with its own exact-key validation,
  atomic write, and reader. Its envelope state is `current`, `stale`, or `unavailable`;
  fresh means strictly under `ROSTER_MAX_AGE_HOURS` (24h).
- Store memberships once as `{id,user_id}`. Derive the existing `student_ids` convenience
  list in memory when adapting a valid snapshot for Roster; do not persist duplicate IDs.
- The existing `load_group_categories()` remains the live acquisition and mutation-validation
  owner. Roster snapshots only its successful normalized result; do not copy its specialized
  HTTP fallback transport into CanvasMirror.
- Invalidation follows only confirmed Canvas writes from Roster membership updates and
  group/group-set creation. It marks local state stale rather than attempting an optimistic
  membership merge.
