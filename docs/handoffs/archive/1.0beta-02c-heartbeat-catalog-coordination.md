# Extend coordinated assignment acquisition to heartbeat/manual-sync passes

Status: **SPEC; ready for execution**

Risk: **medium** - read-only Canvas receipts already proven safe for one consumer pair
(01f, C, 12b1r) - Course Catalog is now fed by the private mirror's `full_pass`/`delta_pass`
too; no Canvas mutation is authorized, and Catalog's schema/allowlist/validation are unchanged.

Depends on: source HEAD `f1135b4` (Batch 4 precision grading, GREEN) plus accepted slice 02a

## Teacher-visible result

The Course Catalog (assignment names/points/dates/rubrics) stays fresh automatically as the
private mirror's background heartbeat runs, without the teacher needing to click "Refresh
Course Catalog" and without any extra Canvas call beyond what the heartbeat already makes
every tick.

## Background (read before writing code)

`docs/handoffs/archive/1.0beta-02a-coordinated-assignment-acquisition.md` (GREEN, completed)
already solved the narrow case: the manual `POST /api/course-catalog/refresh` route acquires
the Canvas assignment collection once and feeds that in-memory receipt to both Course Catalog
and the private mirror's assignment-membership index. Its explicit non-goal was: "Do not
coordinate heartbeat/full/delta passes with Catalog refresh beyond reusing the narrow
acquisition helper." Vision doc §21 item 5 ("duplicate Course Catalog/private-mirror
assignment acquisition") still lists this without a "(resolved by …)" tag — this brief closes
the remaining gap: the private mirror's `full_pass`/`delta_pass` (15-minute heartbeat, nightly
reconcile, and manual "Sync now") independently re-fetch the assignments collection today and
never touch Catalog at all.

There is no stated design law anywhere (vision doc §5, §22 non-goals, `AGENTS.md`, the catalog
contract, or 02a itself) that Catalog refresh must stay manual-only forever. The 02a non-goal
is a slice-boundary statement, not a product principle — vision §5.3 ("one acquisition may
feed multiple projections") and §9.1 (Catalog's `course_structure.*` scopes eventually joining
the same coordinated model) both point toward exactly this extension.

## Acceptance criteria

- [ ] Every `full_pass`/`delta_pass` invocation (heartbeat tick, nightly reconcile, or manual
  `sync_now`) forwards its already-acquired assignment receipt to Course Catalog's assignment
  scope — no second Canvas call for assignments is made on behalf of Catalog.
- [ ] The forwarded receipt is applied regardless of whether the mirror pass itself continues
  or aborts on `assignment_error` — Catalog decides its own last-good/incomplete/current state
  independently, per §5.3/§7.5. A bad receipt must not corrupt Catalog, and a good receipt must
  not be dropped just because the mirror pass later fails on students/submissions.
- [ ] Catalog's `modules` and `assignment_groups` scopes are **not** re-fetched from Canvas by
  this path — their previously-committed values pass through unchanged (same records, same
  `state`/timestamps) unless there was no previous catalog at all, in which case they take the
  existing "unavailable, no previous, empty records" shape already used elsewhere in this file
  for a missing scope.
- [ ] A failure while updating Catalog (write error, corrupt file, unexpected exception) never
  raises out of `full_pass`/`delta_pass` and never changes that pass's own `ok`/return value —
  the two projections remain independently durable, exactly as 02a established for the manual
  route.
- [ ] `GET /api/course-catalog` remains disk-only; no new Canvas call, schema field, allowlist
  entry, or persistence format is introduced. `POST /api/course-catalog/refresh` behavior is
  unchanged.
- [ ] All pre-existing `full_pass`/`delta_pass`/heartbeat/`sync_now` tests still pass (updated
  deliberately if their fixtures now also touch a Catalog file - not accidentally broken).
- [ ] The named acceptance gate passes.

The executor reports evidence; the senior accepts only when every criterion holds.

## Explicit non-goals

- Do not create a general coordinator, typed read service, registry, cache, or new endpoint.
- Do not fetch or coordinate modules or assignment-groups for Catalog from this path — those
  stay live-fetch-only, owned by `refresh_catalog`'s existing executor pool, untouched by this
  brief. (There is no mirror-side module/assignment-group acquisition to share: the mirror
  fetches only assignments + submissions + roster; confirmed by full read of `api/mirror/`.)
- Do not alter Catalog schemas, allowlists, `CATALOG_VERSION`, validation rules, or the
  existing manual-route coordination helper from 02a.
- Do not alter mirror submission/roster passes, lifecycle/circuit behavior, New Quiz metadata
  sync, Current-course policy, watermark semantics, or Canvas writes.
- Do not touch `roster_pass` (it never fetches assignments).
- Do not add a `course_name` plumbing path beyond the two call sites named below
  (`run_heartbeat_pass`, `sync_now`) - no UI change, no config schema change.

## Locked decisions

- Add `course_catalog.refresh_catalog_assignments_only(course_id, *, assignment_receipt,
  root=None, attempted_at=None, course_name=None)`. Modeled directly on `refresh_catalog`
  (`api/course_catalog.py:812-864`): reuse `_course_lock`, `read_catalog`, and the
  `previous_assignments`/`previous_modules`/`previous_groups` extraction verbatim; drop the
  `ThreadPoolExecutor` module/assignment-group legs entirely; always take the receipt branch
  (`_assignment_scope_from_receipt`, already a pure function with zero Canvas calls,
  `api/course_catalog.py:471-515`); set `modules`/`assignment_groups` to their previous values
  unchanged, falling back to the same "unavailable, empty records" stub shape the file already
  uses for a scope with no previous data when there is no previous catalog at all; assemble and
  `write_catalog` the combined document exactly as `refresh_catalog` does (one JSON document
  per course - there is no per-scope file to write independently, per the existing storage
  shape). When `course_name` is not supplied, fall back to the previous catalog's stored
  `course_name`, else `course_id` — matching the existing `_normalize_text(course_name) or
  course_id` fallback already in `refresh_catalog`.
- In `api/mirror/sync.py`, add an optional keyword-only `course_name: str | None = None` to
  `full_pass` and `delta_pass`. Immediately after the existing assignment-receipt acquisition
  (`full_pass` around line 325-326; `delta_pass` around line 389-390) and **before** the
  `if assignment_error:` early-return in each, call
  `course_catalog.refresh_catalog_assignments_only(course_id, assignment_receipt=(assignments,
  error, complete), course_name=course_name, root=root, attempted_at=started)` inside a
  `try/except Exception` that only logs/absorbs - it must never affect `assignment_error`,
  the pass's control flow, or its returned dict. Placing the call before the early-return is
  deliberate: Catalog must still receive a good receipt (or apply its own incomplete handling
  to a bad one) even when the mirror pass itself aborts.
- In `api/webui/mirror_service.py`, thread `course_name=course.get("name")` into the `kwargs`
  dict built at `run_heartbeat_pass` line ~108 for `full`/`delta` pass kwargs only (not
  `roster`), and into the `sync.delta_pass(...)` call inside `sync_now` (line ~151-153). Both
  functions already iterate `config.active_courses()`, the exact same source
  `course_catalog._current_course()` reads for its Current-course gate - confirm this in
  preflight; if it does not hold, stop (see Stop conditions).
- Update only the coordinated-receipt paragraph in `docs/mirror.md` and the `Acquisition and
  writes` section of `docs/contracts/course-catalog-contract.md` to state that `full_pass`,
  `delta_pass`, and the manual Catalog-refresh route all now forward their assignment receipt
  to Catalog's assignment scope only, non-transactionally, with modules/assignment-groups left
  untouched by the pass-driven paths.

## Stop conditions

- **RED:** the "current course" sets read by the mirror heartbeat and by
  `course_catalog._current_course()` are not provably the same set; sharing the receipt would
  require live-fetching modules/assignment-groups from this path; or a public Catalog schema
  change is needed.
- **YELLOW:** `_assignment_scope_from_receipt`'s existing incomplete/invalid handling produces
  a Catalog state that materially disagrees with what the mirror does with the same bad receipt
  in a way that looks like a product decision rather than the already-accepted 02a behavior
  (02a already accepted that these two consumers can reach different last-good states from the
  same receipt - only flag genuinely new disagreement, not a repeat of that accepted fact).
