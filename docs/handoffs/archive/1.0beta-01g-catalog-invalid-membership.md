# 1.0beta slice 01g — Catalog invalid-record membership safety

Status: **ACCEPTED**

Risk: **medium** — prevents a student-free Course Catalog refresh from deleting existing
assignment/module membership after a complete transport response contains an invalid or duplicate
top-level record. No Canvas write, private-mirror, credential, browser, or live-data action is
authorized.

Depends on: accepted 01f authoritative empty Catalog semantics (`0a3fe58`).

## Teacher-visible result

A bad assignment or module record from Canvas no longer makes already-known Catalog entries
disappear. The Catalog retains its last-good list and labels the scope incomplete; a first-ever
refresh may still show its valid subset honestly as incomplete, rather than claiming an empty or
complete catalog.

## Locked design

### 1. Validate complete top-level membership before replacement

For a complete top-level assignment receipt, normalize every row with the existing normalizer and
require distinct normalized assignment IDs. For a complete top-level module receipt, require a
valid normalized module ID on every row and distinct module IDs before its list can replace
existing membership.

- A missing/invalid top-level record or duplicate normalized ID is `incomplete`, not an
  authoritative deletion. Use stable codes `invalid_assignment_record` and
  `invalid_module_record` respectively; do not persist raw record details.
- Keep 01f's proven-empty behavior unchanged: an actual `[]` still clears the scope as current.
- Keep all 01e/01f receipt failure codes and current transport mapping unchanged.

### 2. Last-good-safe incomplete result

Add a focused private Catalog helper rather than overloading `_scope_failure` ambiguously.

- If the corresponding prior scope has a valid `last_success_at`, retain its records exactly,
  set `state: incomplete`, preserve `last_success_at`, set `last_attempt_at` to the new attempt,
  and record the stable invalid-record code. This includes a last-good authoritative empty scope.
- If no prior successful scope exists but the fresh collection contains one or more valid unique
  records, persist just that valid subset as `incomplete`, set no `last_success_at`, and record
  the same invalid-record code. It is useful bootstrap data, not complete membership proof.
- If no prior success and no valid records exist, use the existing unavailable shape with the
  stable invalid-record code; do not create a fictional incomplete empty success.

The `assignments` and `modules` scopes retain their existing independent merge behavior. A bad
assignment list must not block a valid modules update; a bad module list must not block a valid
assignment update.

### 3. Preserve scope boundaries and durable truth

Do not change `refresh_catalog` signature, the 01e complete receipt, Catalog v1 schema/path,
strict persisted allowlists, Current-course route, atomic/previous-file behavior, or public
projection shape. Do not treat invalid nested module items, missing item fallback, malformed
rubric details, or non-top-level field coercion as a reason to broaden this slice.

Update `docs/contracts/course-catalog-contract.md` only to state that invalid/duplicate
top-level records preserve last-good membership (or expose a first-sync valid subset as
incomplete). Existing `incomplete` module-item fallback semantics remain as written.
