# Reconcile the exact group scope right after a group/membership write

Status: **READY**

Risk: **medium** - touches the Roster group-write success path; the live Canvas write itself
is unchanged, only what happens to local mirror state after a confirmed success changes.

Depends on: source HEAD `0632497` (Batch 2's Course Info half + Batch 3/4 all GREEN)

## Teacher-visible result

After a teacher creates a group set, creates a group, or moves a student between groups,
Roster, Course Info, the differentiated-assignment picker, and Home's roster warnings all
show the correct membership immediately on their next read — but only the one group category
that actually changed causes a Canvas call. Every other category in the course is served from
the untouched local snapshot instead of being needlessly re-fetched, which today happens on
every single group write regardless of how many categories/groups/memberships the course has.

## Background (read before writing code)

`docs/handoffs/archive/1.0beta-03f-roster-private-groups-snapshot.md` (GREEN) built the
private `groups.v1.json` snapshot and locked its reconciliation mechanism as
"invalidate-then-lazy-reacquire": every successful group/membership write already calls
`mirror_store.invalidate_groups(course_id)`, which marks the **entire** document `state:
"stale"`. The next read of *any* category then falls back to `load_group_categories()` — a
full live re-fetch of every category, every group, and every membership in the course,
regardless of which single category actually changed.

`docs/handoffs/archive/1.0beta-03i-course-info-local-spine.md` is the first place this gap was
named explicitly, as a deliberate non-goal: *"Do not add per-group targeted invalidation;
course-wide `groups.v1.json` staling stands."* Vision doc §17.1 row 2 ("People context
completion") names the remaining outcome directly: *"make group mutations reconcile the exact
group scope promptly."* §14.1's normative command sequence names the same idea at step 9:
*"request targeted mirror reconciliation."* §14.2's mutation-to-scope map confirms the two
consumer surfaces this covers: *"Group/category/membership change → Groups/memberships;
roster-warning views."*

Senior decision already made (do not revisit): keep this synchronous and inline in the
existing write request — no new delayed/fire-and-forget notify infrastructure like
1.0beta-03a's `notify_course_changed()` for submissions. Groups' write paths already make
multiple synchronous Canvas calls per request (e.g. category-then-groups); one more scoped GET
for reconciliation fits that existing shape and needs no new async machinery.

## Acceptance criteria

- [ ] After each of the four existing group-write success points — `update_student`'s
  `canvas_group` branch, `update_bulk`'s `set_canvas_group`/`clear_canvas_group` actions,
  `create_group_set`, and `create_groups` — a targeted reconciliation runs instead of the
  whole-snapshot `invalidate_groups` call: it live-refetches only the affected category's
  groups and memberships from Canvas and merges just that one category into the existing
  `groups.v1.json`, leaving every other category byte-identical.
- [ ] The merge only ever happens against an existing, previously-written groups document. If
  no previous document exists for the course, targeted reconciliation is skipped and the
  existing whole-document `invalidate_groups` path runs instead (unchanged from today) — a
  lone category is never written as if it were the course's complete membership (vision
  §10.1: "a complete collection defines membership").
- [ ] If the targeted live re-fetch fails (Canvas error, timeout, non-200) or the merge write
  fails (`OSError`/`ValueError`), reconciliation falls back to the existing whole-document
  `invalidate_groups(course_id)` call — never raises, never leaves a changed category silently
  marked current with stale data, and never behaves worse than today.
- [ ] After a successful targeted reconciliation, the merged document's envelope `state` is
  `"current"` and its timestamps reflect the reconciliation time. Every existing read
  consumer — `courses.py::list_groups`, `courses.py::_local_group_sets`,
  `roster.py::_group_categories_for_roster`, `roster_warnings.py::scan_course`,
  `read_service.py::private_groups` — needs **zero** code changes and keeps working through
  the exact same `read_groups`/`groups_are_current`/`groups_for_roster` calls it uses today.
- [ ] No Canvas call is made for categories that did not change. A test proves that a
  membership change inside one category makes no Canvas request naming any other existing
  category's id.
- [ ] `groups.v1.json`'s schema/envelope is unchanged: `_GROUPS_KEYS`, `PASS_STATES`,
  `_validate_groups_categories`, and `validate_groups` keep their current exact-key contract —
  no new persisted field.
- [ ] The named acceptance gate passes.

The executor reports evidence; the senior accepts only when every criterion holds.

### Deviations / design notes

- **`create_groups` partial-failure reconciliation (not explicitly specced):** the brief locks
  "move the reconciliation call to run once after the creation loop completes," addressing the
  happy path. Today's per-success-call behavior also reconciles whatever was already created
  before a later group in the same multi-group request fails. Moving the call to run only after
  a fully successful loop would silently regress that case (a partially created set of groups
  would never be reconciled by this request). I added one extra call on the failure branch —
  `invalidate_groups(course_id, str(category_id))` — guarded by `if created_groups:` (i.e. only
  when at least one group actually got created before the failure), so a multi-group request
  still reconciles at most once regardless of outcome, and partial success is never worse than
  today. This is an additive safety preservation, not a new design; the senior has not flagged
  this one.
- **`create_group_set`'s reconciliation timing — resolved by senior direction (was flagged as an
  open question in the prior executor pass; now fixed, not a design choice left open):** the
  first executor pass implemented the locked decision literally — `roster_groups.py:53`'s
  reconciliation call fired right after category creation, before the seed-groups loop, matching
  the *location* the brief named (which only instructed adding args, not relocating the call,
  unlike `create_groups`). The senior reviewed and confirmed this was a real regression the
  acceptance criteria don't permit, not a benign ordering quirk: today's *old* whole-document
  `invalidate_groups(course_id)` was safe at that early timing only because it staled the *whole*
  document, so the *next* read naturally re-did a full live `load_group_categories()` that picked
  up whatever got seeded afterward. The new targeted `merge_group_category` has no such safety
  net — firing it before the seed loop merges in a category that legitimately has zero groups yet
  and writes it as `state: "current"`, with nothing to ever re-reconcile it afterward unless an
  unrelated future write happens to touch the same category. That is a real, teacher-visible bug
  (a group set created with seed groups would show 0 groups indefinitely in Course Info / the
  differentiated picker / Roster), not an acceptable trade-off.
  **Fix applied:** moved `create_group_set`'s reconciliation call out from right after category
  creation to run once *after* the seed-groups loop completes, mirroring `create_groups`'s
  pattern exactly, including the same partial-failure safety net — if a seed group fails partway
  through, the successfully-created groups so far are still reconciled (guarded by
  `if created_groups:`, same as `create_groups`) before the error is returned; on full success,
  reconciliation runs once, unconditionally, after the loop. `category.get("name")` is threaded
  through to this new call site (still needed since this is a genuinely new category with no
  previous entry). Proved by two new tests:
  `test_create_group_set_reconciliation_shows_seeded_groups_not_zero` (asserts the exact Canvas
  call order — both seed-group creations happen before the targeted fetch — and that the merged
  snapshot shows both seeded groups, with an unrelated pre-existing category left untouched) and
  `test_create_group_set_partial_failure_reconciles_created_groups` (one seed group rejected by
  Canvas; asserts the merged snapshot still shows the one group that *did* get created). The
  existing `test_create_group_set_with_groups` was also strengthened to assert the reconcile call
  now lands strictly after both group-creation Canvas calls, not before.
- **`create_group_set`'s failure-branch guard — second, narrower senior correction (resolved,
  not left open):** after the timing fix above, `create_group_set`'s failure branch still copied
  `create_groups`'s exact guard, `if created_groups: invalidate_groups(...)`. The senior caught
  that this guard is correct for `create_groups` (an *already-existing* category — if the first
  new group fails, nothing in Canvas changed for that category, so skipping is right) but wrong
  for `create_group_set`: its category-creation POST already succeeded unconditionally *before*
  the seed loop starts, so a real new category exists in Canvas regardless of whether zero, some,
  or all seed groups also succeed. With the guard in place, a first-seed-name failure
  (`created_groups == []` at that point) skipped reconciliation entirely, leaving that real new
  category silently absent from the mirror indefinitely — a narrower recurrence of the same class
  of bug, still worse than today and still ruled out by "never behaves worse than today."
  **Fix applied:** removed the `if created_groups:` guard from `create_group_set`'s failure
  branch only — `invalidate_groups(course_id, category_id, category_name)` now runs
  unconditionally there. `create_groups`'s guard is untouched (correct as-is; no category-level
  change occurs there if nothing was created). Proved by a new test,
  `test_create_group_set_first_seed_failure_still_reconciles_new_empty_category`: the very first
  seed group name fails, and the merged snapshot still shows the new category present with zero
  groups (not absent), while an unrelated pre-existing category stays untouched.
- Every other implementation choice matches the brief's locked decisions verbatim (function
  signatures, call-site line numbers/behavior, fallback shape, `Callable` type-hint updates).
